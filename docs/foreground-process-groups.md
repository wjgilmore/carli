# Foreground process groups and signals

carli isolates every interactive external command in its own Unix process
group and temporarily gives that group control of the terminal. This prevents
terminal-generated signals intended for a command from also interrupting or
suspending the shell.

This document describes the implemented behavior. For broader background on
why shells need signals, see [Why Signal Handling Matters in Shell
Development](signal-handling.md).

## Terminal ownership

A controlling terminal records one process group as its foreground process
group. That group receives terminal input and signals generated by special
characters such as <kbd>Ctrl-C</kbd> and <kbd>Ctrl-Z</kbd>.

When carli starts interactively, it first verifies that its inherited process
group owns the terminal. If carli was launched in the background, it stops with
`SIGTTIN` until its parent moves it to the foreground. It then places itself in
its own process group, ignores the terminal-control signals that should not
suspend the shell, and claims the terminal. Running `sleep 60`, for example,
changes the relationship temporarily:

```text
Before the command         While sleep is running       After sleep exits

Terminal                   Terminal                     Terminal
  |                          |                            |
  +-- carli (foreground)     +-- sleep (foreground)      +-- carli (foreground)
                             |
                             +-- carli (waiting)
```

For each interactive external command, carli performs these steps:

1. Fork and prepare the child process.
2. Create a process group whose ID is the child's process ID.
3. Restore default signal behavior in the child.
4. Assign the terminal to the child's process group with `tcsetpgrp`.
5. Wait for the child to exit, be terminated, or stop.
6. Assign the terminal back to carli's process group.
7. Record the result for `$?` and display the next prompt.

The child and parent both attempt to establish the child process group. Doing
so on both sides closes the race in which either process might run first after
the fork.

## Signal behavior

carli ignores these signals while acting as the interactive shell:

- `SIGINT`, normally generated by <kbd>Ctrl-C</kbd>;
- `SIGQUIT`, normally generated by <kbd>Ctrl-\</kbd>;
- `SIGTSTP`, normally generated by <kbd>Ctrl-Z</kbd>;
- `SIGTTIN`, sent when a background group attempts to read the terminal; and
- `SIGTTOU`, sent for certain background terminal operations.

The line editor temporarily installs its own `SIGINT` handler while reading a
command, so <kbd>Ctrl-C</kbd> still cancels the current input and produces a
fresh prompt.

Before an external program begins, carli restores the default disposition for
all five signals in the child. Once the child owns the terminal, controls such
as <kbd>Ctrl-C</kbd> and <kbd>Ctrl-Z</kbd> therefore affect the child process
group and not carli.

## Exit and signal statuses

A program that exits normally supplies its own status. A program terminated by
a signal produces `128 + signal_number`, following the usual shell convention.
For example, interrupting a foreground command with `SIGINT` produces status
`130`:

```sh
sleep 60
# Press Ctrl-C
echo $?
# 130
```

If a foreground command stops, carli records `128 + stop_signal`. A command
stopped by `SIGTSTP` therefore normally produces status `148`.

## Stopped commands

carli detects stopped children with `waitpid(..., WUNTRACED)` and immediately
reclaims the terminal, so <kbd>Ctrl-Z</kbd> cannot leave the shell blocked behind
a suspended command. It reports the stopped command and retains enough
information to monitor and clean up its process group.

Full job control is not implemented yet. In particular, carli does not yet
provide `jobs`, `fg`, or `bg`, so a stopped command cannot currently be resumed
through a carli built-in. If a retained job exits or is terminated by another
process, carli reaps it before displaying a later prompt. When carli exits, it
sends `SIGHUP` followed by `SIGCONT` to remaining stopped process groups so they
do not remain abandoned indefinitely.

## Non-interactive execution

When standard input is not a terminal, carli does not transfer terminal
ownership or create interactive foreground jobs. It waits for external commands
normally and still translates signal termination into `$?`. This keeps input
from files and other non-terminal sources working without attempting terminal
operations on them.

## Failures and recovery

If process-group creation or terminal transfer fails, carli reports the error,
terminates the child group when necessary, and does not wait indefinitely for a
program that cannot correctly own the terminal. After every normal exit,
signal termination, or stop event, carli attempts to reclaim terminal ownership
before reading another command.

Terminal ownership and terminal modes are related but distinct. Programs such
as Vim normally restore their own terminal modes when they exit. Additional
terminal-mode snapshot and recovery work may still be useful for programs that
crash after changing terminal attributes.

## Manual verification

These scenarios exercise the principal behavior:

```sh
sleep 60
# Ctrl-C should stop sleep, not carli; `echo $?` should print 130.

cat
# Ctrl-Z should stop cat and return a usable carli prompt.

vim /tmp/carli-signal-test.txt
# Exiting Vim should return to a usable prompt.
```

Process groups and terminal ownership can also be observed from another
terminal with `ps`:

```sh
ps -o pid,ppid,pgid,tpgid,state,command
```

While a foreground child is running, its `PGID` should match the terminal's
`TPGID`. After it exits or stops, carli's process group should match `TPGID`
again.
